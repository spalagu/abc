# 0.1.2：权限入口修复

## 这次确认的缺陷

0.1.1 并没有两套独立的授权按钮：一个按钮连续请求辅助功能和录屏，另一个“打开系统隐私设置”却固定跳到辅助功能。也没有独立的录屏设置入口。请求的即时返回值没有说明，提示还把下载的 .app 当成 Terminal/Python 源码进程。这些是 Demo 自己的引导问题。

系统录屏列表没有应用条目时，不应仅凭截图认定是签名问题。临时签名升级、启动位置和系统授权状态都可能影响结果；本次修复不声称根治签名身份或 TCC 的全部问题。

## 新界面

| 权限行 | “请求权限” | “打开…设置” |
|---|---|---|
| 辅助功能 | 只调用 AXIsProcessTrustedWithOptions | Privacy_Accessibility |
| 录屏与系统录音 | 只调用 CGRequestScreenCaptureAccess | Privacy_ScreenCapture |

两种请求不串联；打开设置不自动请求或授予权限。请求后也不会用第二个弹窗或另一个设置页覆盖系统对话。新 Host 显示当前进程状态、当前运行应用/可执行文件路径，并提供“重新检查授权”和“在 Finder 显示当前程序”。从设置返回 Host 时重新查询状态。系统设置快捷 URL 不能保证所有 macOS 版本都正确定位，所以始终给出手动路径。

本地运行路径仅显示在 Host 窗口，不增加远端接口字段，也不导出到诊断 JSON。源码模式不把 Python.app 冒认为 WorkContinuity.app；授权对象以系统弹窗为准。应用位置信息不是 TCC 责任进程归属的证明。

## 列表里没有 Demo，现有版本也能处理

在“系统设置 → 隐私与安全性 → 录屏与系统录音”上方列表点“＋”，选择你实际启动的 WorkContinuity.app 并开启。不要加到“仅系统录音”里；不要为了这个 Demo 授权其他不相关应用。完整退出 Demo 后从同一份 .app 重新打开，用新配对地址连接。

这一步不需要再次运行 tccutil，不删除现有工作，也不关闭 Lens/Codex。若你仍在下载目录运行，先完整退出，把应用放到“应用程序”后再对那一份授权，避免混用多个副本。

## 验收

只检查三件事：两行设置按钮分别定位对应权限；录屏请求只触发录屏授权流程；手动添加当前应用并授权重开后，Host 状态和实际读取/截图结果一致。若没有系统弹窗，使用对应设置行的手动添加路径，而不是反复点合并按钮。授权由 macOS 与用户确认完成，程序不会自动点允许、修改 TCC 数据库或绕过系统策略。

## 测试范围

新增 12 项无授权单元回归：独立请求、失败不串联、拒绝返回值、URL/按钮绑定、打包/源码提示、当前运行路径、未知权限拒绝。Mac UI 冒烟检查实际按钮标题/selector 和原生窗口创建；打包冒烟检查 frozen 可执行程序找到当前 .app 及 Bundle ID。既有输入、图像和浏览器回归仍保留。

自动检查不代表用户机器的 TCC 列表已经更新，不代表真实系统设置页面跳转/授权实测通过。仍使用 ad-hoc 签名，未新增稳定开发者签名。不得宣称以后更新不再需要重新授权。
